Quickstart

You need a current stable Rust toolchain with Cargo, Git, a supported coding client, and an OpenAI Platform API key. Choose a model available to your API project that supports both Responses and Batch. See the OpenAI model reference.

The setup below uses Bash or Zsh on macOS or Linux. Kaiiron is currently distributed as source.

1. Install and start Kaiiron

git clone https://github.com/PatrickAuld/Kaiion.git
cd Kaiion
cargo install --path . --locked
kaiiron --mode batch start
kaiiron status

The proxy listens on http://127.0.0.1:8787. Make sure Cargo’s binary directory is on your PATH. If Kaiiron is already running, stop it before starting it with a different mode.

2. Connect Codex

kaiiron configure --client codex

This selects Kaiiron as Codex’s provider and updates its Responses transport settings while preserving unrelated configuration. It keeps your configured Codex model. To inspect which files would be updated first, add --dry-run.

3. Supply credentials and run a small task

Set OPENAI_API_KEY in the shell that launches your client, using your normal secret-management process. In the following command, replace YOUR_BATCH_SUPPORTED_MODEL with your model ID. Run it from a repository you want the agent to inspect.

codex exec --sandbox read-only \
  --model YOUR_BATCH_SUPPORTED_MODEL \
  "Read the README and suggest three documentation improvements. Do not edit files."

Keep the client running while it waits. Kaiiron sends progress events during batch processing and returns the completed response. This is billed API inference, separate from a ChatGPT subscription.

Plan for provider latency. OpenAI batches have a 24-hour completion window; unfinished work can expire. A tool-using agent can need several dependent inference calls, each with its own wait. Client timeouts still apply. There is no overnight completion guarantee.

Client setup

OpenCode

Choose a model ID and a workflow ID. Replace YOUR_BATCH_SUPPORTED_MODEL in both commands.

kaiiron configure --client opencode \
  --model YOUR_BATCH_SUPPORTED_MODEL \
  --client-mode batch --session-id docs-review-001
opencode --model kaiion/YOUR_BATCH_SUPPORTED_MODEL

Pi

kaiiron configure --client pi \
  --model YOUR_BATCH_SUPPORTED_MODEL \
  --client-mode batch --session-id docs-review-002
pi --provider kaiion --model YOUR_BATCH_SUPPORTED_MODEL

Keep the session ID stable across retries of the same workflow. Configure a new ID for a new workflow. A static session header cannot distinguish an intentional, identical inference from a retry. Custom adapters should send a unique Idempotency-Key per intended inference and reuse it only for that inference’s retries.

Codex normally supplies its own stable session metadata. Explicit --client-mode and --session-id options are also available for Codex and take precedence when set. Existing explicit mode headers remain until changed; use --client-mode batch to replace a prior direct override.

Claude Code

Not supported in this release. Claude Code requires Anthropic Messages, and Kaiiron currently exposes OpenAI Responses. kaiiron configure --client claude rejects configuration instead of writing an incompatible endpoint.

Routing modes

Batch submits each inference as a one-entry provider batch. Direct passes the request through immediately. Auto chooses using a deterministic policy with your model prices, a maximum estimated direct cost, and a maximum estimated premium for avoiding the wait.

To enable auto, first copy and edit the example policy with your model IDs and current provider rates. Its prices are illustrative. Then restart the service with an absolute path to your policy:

kaiiron stop
kaiiron --mode auto \
  --routing-policy /absolute/path/routing-policy.json start
kaiiron jobs route --request examples/response-request.json

The last command runs from the cloned repository and explains the route without calling the inference provider. To route OpenCode or Pi through auto, repeat that client’s configuration with --client-mode auto and a stable session ID. Explicit client headers override the proxy default.

Unknown model prices, missing output limits, substantial reasoning settings, and unpriced modalities or hosted tools favor batch. With no policy file, auto selects batch. The policy loads on startup; restart to reload it.

Limits are per-call estimates, not cumulative budgets or billing guarantees. Direct calls—including auto-selected direct calls—do not have durable batch replay semantics. Existing batch jobs stay on batch when replayed through auto.

Detached inference jobs

Use the job API when your caller should submit inference and return immediately. Set OPENAI_API_KEY, edit the example request’s model and input, and run these commands from the cloned repository:

kaiiron jobs submit \
  --request examples/response-request.json \
  --idempotency-key workflow-42/step-1
kaiiron jobs list
kaiiron jobs show JOB_ID
kaiiron jobs wait JOB_ID

Replace JOB_ID with the submitted job’s ID. wait reattaches credentials, polls, and prints the stored response. Interrupting it leaves the inference running while the proxy stays up. Detached jobs always use batch, regardless of the proxy’s default mode.

After a proxy restart, use kaiiron jobs resume JOB_ID or wait to restart polling. The optional --resume-from-env service flag resumes matching jobs using OPENAI_API_KEY and any matching organization/project variables.

These are inference jobs. Your harness remains responsible for saving tool results, workspace state, and the next step in an agent workflow.

Recovery and release limits

Kaiiron persists batch request bodies, upstream job IDs, and terminal results in SQLite. When a client reissues the same identified request with matching credentials, Kaiiron reconnects to its pending batch or replays its stored result.

  • No automatic agent restoration. Stock Codex does not resend an interrupted inference merely because codex resume starts. An agent continuation adapter or an explicit request replay is required.
  • Credentials are not stored. Resumption requires the original API key, organization, project, and upstream provider. Key rotation across existing jobs is not yet supported.
  • Uncertain submissions stay explicit. If the provider may have accepted a batch but its create response was lost, Kaiiron reconciles provider metadata. It does not blindly create another potentially billable batch.
  • Batch requests need full history and stable identity. Use an idempotency key, session header, or supported client metadata. Batch mode rejects store: true, previous_response_id, conversation, and background: true.
  • One process per database. Request pooling, native Anthropic and Chat Completions adapters, workflow supervision, and hard cumulative budgets are not included.

For the detailed contract and upcoming work, read the architecture and roadmap.

Local operations

kaiiron status
kaiiron logs --lines 100
kaiiron restart
kaiiron stop

restart reuses the saved service configuration and working directory. For a different configuration, stop the service and start it with the new options.

Configuration lives in ~/.config/kaiion; the database and service state live in ~/.local/state/kaiion. Kaiiron honors XDG_CONFIG_HOME and XDG_STATE_HOME. The kaiion and kaiiron binaries are equivalent; existing directory names and KAIION_* environment variables retain their original spelling.

If your first request fails

  • Confirm the proxy is healthy with kaiiron status and inspect kaiiron logs --lines 100.
  • Confirm the client shell has the API key and the selected model is available to your project through Batch.
  • For HTTP 400, check full-history requirements and stable session identity. For HTTP 409, check whether an idempotency key was reused with a different payload.
  • For an interrupted agent, consult the recovery contract above before attempting another request.
