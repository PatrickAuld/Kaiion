THE KAIIRON SCHEDULING PLAN

Make room for
the next request.

An agent can wait. A person often can’t. Kaiiron can spread live inference across a provider’s capacity window, give active sessions a better place in line, and queue work behind a busy local model.

Opt in with a policy file. Request, token, and concurrent-call limits run in one Kaiiron process; durable scheduling and dollar budgets are later phases.

WHY SCHEDULE

One slot or a million tokens.
Both need a queue.

LOCAL INFERENCE / AVAILABLE NOW

Protect a single busy model.

An OpenAI-compatible local endpoint may only handle one useful inference at a time. Set max_concurrency: 1 for that provider or model. Kaiiron holds later calls until the live request releases its slot, while still applying any request or token ceilings.

SPEND SMOOTHING / IN DESIGN

Keep a surge from becoming a bill.

Request and token windows can pace a large jump in usage today. A future dollar budget will reserve estimated cost across in-flight calls, reconcile provider usage, and bound spend by a configured window. Existing per-call cost routing does not enforce a cumulative budget.

THREE WAYS THROUGH

The request chooses a lane.
The scheduler chooses a time.

01 / LIVE

Answer now

When scheduling is off, direct requests keep the existing live passthrough behavior.

02 / SCHEDULED LIVE

Wait for a slot

With a policy enabled, a live request waits until every matching provider and model limit permits dispatch.

03 / BATCH

Give it more time

Explicit Batch stays Batch. Auto can move eligible, patient work there before a live call begins.

THE DECISION PATH

Capacity first. Priority second.

No priority can spend capacity that the policy has reserved for another request.

  1. 01

    Read the request

    Resolve the provider model, session, estimated tokens, and whether this is a user prompt or a tool continuation.

  2. 02

    Check every limit

    Compose provider-wide and per-model concurrent-call, request, input, output, and total-token limits.

  3. 03

    Order eligible work

    Consider cache timing, recent human activity, expected complexity, wait-tolerant aliases, and time already spent in line.

  4. 04

    Dispatch and observe

    Send the unchanged live request except for a resolved async- model name. Reconcile token usage when the response provides it.

RULES THAT COMPOSE

A queue with a reason.

Hard limits decide when a request is eligible. Session signals decide which eligible request goes next.

↔

Smooth the quota window

Cap concurrent live calls and rolling request counts, pace RPS and token use, and apply all matching provider and model ceilings. Provider limits aggregate credentials unless a rule opts into credential scope.

◷

Keep cache opportunities close

A recent continuation on the same model can earn priority when the prior session showed a cache read. The window is a scheduling hint, never a promised cache hit.

●

Notice a person waiting

A quick new user prompt can rise above tool-only continuations. As the session sits idle, its boost fades; queued work ages forward.

◇

Classify the work

A built-in heuristic considers token estimates, tools, and reasoning effort. An in-process classifier can replace it without changing the quota rules.

⌁

Signal that time is flexible

async-<model> is a virtual model name. Kaiiron removes the prefix upstream, allows a longer bounded wait, and gives it a lower-priority hint.

↗

Recover within bounds

Known retryable failures re-enter admission and honor Retry-After. Auto may choose Batch for a compatible low-priority request before duplicating live work.

A CONCRETE POLICY

Set the ceiling.
Leave the timing to Kaiiron.

A provider-wide rule and a model rule both apply. A request waits for the first time it fits every matching constraint. The values here illustrate the shape of a policy, not a provider’s published limits.

THE RELEASE PATH

Working now. More to make durable.

The first release protects one running process. The next stages address restarts, long waits, and provider feedback.

01AVAILABLE NOW

Scheduled live lane

Composable quotas and concurrent-call caps, paced dispatch, bounded queue and retries, session priority, classifier seam, async- aliases, and eligible Auto-to-Batch recommendations.

02NEXT

Durability and spend budgets

Persist queue metadata, reservations, and attempt state without storing API keys. Add a priced, cumulative budget that reserves in-flight spend and reconciles actual usage; unknown prices must not silently count as zero.

03DESIGN WORK

A better long-wait contract

Give streaming clients progress while queued without inventing provider response IDs or silently changing upstream status and error behavior.

04HARDENING

Feedback and operations

Use provider rate-limit observations, measured versus reserved tokens, queue diagnostics, and load tests to tune headroom and spot stalled work.

WHAT TO EXPECT TODAY

A bounded wait, with visible limits.

Scheduled requests wait before Kaiiron returns HTTP headers. There is no queue heartbeat in this release, so a client with a short timeout can disconnect. The queue and quota ledger are in memory and reset on restart. Traffic sent directly to the provider shares capacity Kaiiron cannot see.

Token estimates are conservative reservations, not billing guarantees. Provider caching and the completion time of a Batch request remain outside Kaiiron’s control.
